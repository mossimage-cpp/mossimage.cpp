# Turing (sm_75) support

MossInfer builds for NVIDIA compute capability 8.x (Ampere, Ada) and 12.x (Blackwell) by default. A build configured
with `-DMOSSINFER_SM75=ON` also carries a full set of Turing kernels and accepts compute capability 7.5 devices (RTX
20xx, T4, GTX 16xx), so a card such as an RTX 2080 8 GiB can run the whole pipeline: text encoder, DiT and VAE.

Turing has no bf16 tensor cores, no `cp.async`, no TF32 and only 64 KiB of shared memory per block, so the sm_75
kernel family is not a flag on the sm_80 one: it is a second implementation of every tensor-core kernel, compiled for
`sm_75` alone and dispatched at run time by the device's compute capability.

## Build

The Windows CUDA 13 preset builds a complete package and names it with a `-sm75` suffix:

```sh
cmake --preset windows-msvc-cuda13-sm75
cmake --build --preset windows-msvc-cuda13-sm75
ctest --preset windows-msvc-cuda13-sm75 -L '^cpu$'
cpack --config build/windows-msvc-cuda13-sm75/CPackConfig.cmake -B build/windows-msvc-cuda13-sm75
# -> build/windows-msvc-cuda13-sm75/mossinfer-2.2.1-windows-cu13-x86_64-sm75.zip
```

Any other preset takes the option too (`-DMOSSINFER_SM75=ON`), e.g. a Linux build from a custom preset; the ordinary
presets stay Ampere-and-newer. Without the option the engine refuses compute capability 7.5 exactly as before.

## What runs

| Component | sm_80+ build (unchanged) | sm_75 build |
|---|---|---|
| bf16 linears (DiT blocks and globals, text refiner, text encoder) | cuBLASLt bf16 tensor cores | fp16 tensor cores through cuBLASLt: weights are converted to fp16 once at load (or per streamed block), activations are converted in row chunks inside the caller's GEMM workspace (a row above fp16's range is scaled by a power of two, undone exactly), the GEMM writes fp32 and one pass adds the bias in fp32 and rounds once to the output dtype |
| Exact attention | FlashAttention-2 (bf16, `cp.async`) | a dedicated `m16n8k8` fp16 kernel with an online softmax (head_dim 128 non-causal varlen GQA for the DiT, head_dim 256 causal for the text encoder); it reads the bf16 q/k/v directly, converting them as it stages them, and writes bf16 |
| INT8 ConvRot GEMMs (`high` tier) | CUTLASS `m16n8k32` | CUTLASS `m8n8k16` (Turing's INT8 MMA), same epilogues; bit-exact against a host int32 reference |
| INT4 ConvRot GEMMs (`turbo` tier) | CUTLASS `m16n8k64` | the engine's existing INT4 → INT8 unpack fallback (bit-exact, the same path Hopper and Blackwell use) |
| 8-bit attention (`q8_fp16`, `q8_fp8`) | SageAttention kernels | `q8_fp16`: a Turing INT8-QK kernel (sm_75 only, not Volta), run when `attention=q8_fp16` is given; `q8_fp8` is refused. An unset `attention` resolves to `exact` with the reason saying so (the tier is otherwise unchanged) |
| VAE decode | TF32/bf16 CUTLASS implicit-GEMM convolutions, TF32 attention | fp32 SIMT convolutions and a fp32 attention kernel (reference precision; slower, see below) |
| GatedDeltaNet (text encoder) | chunked kernel (~85 KiB of shared memory) | a per-token recurrent kernel that fits 33 KiB; the same rule, fp32 |
| Other kernels (norm, RoPE, elementwise, samplers, group norm, latent preview, …) | compiled for sm_80+ | compiled for sm_75 and sm_80+ from the same source (pure SIMT) |

The DiT blocks run op by op on sm_75: the fused bf16 CUTLASS GEMMs need sm_80+ tensor cores, so the fused route and
its CUDA graphs are not used. Every block path produces the same image, so this only affects speed.

### Tiers on sm_75

`reference` (bf16 bundle), `high` (INT8 ConvRot DiT) and `turbo` (INT4 ConvRot DiT) all run. On sm_75 an unset
`attention` resolves to `exact` and the report's `quality.reason` says "(no default 8-bit attention kernel on this
device)": Turing's `q8_fp16` is no faster than exact there, so it runs only when `attention=q8_fp16` is given (it also
lets `tier high` run on a bf16 DiT). A caller may still pass `attention=exact` explicitly. NVFP4 DiTs are refused as
on every non-Blackwell GPU.

`high` and `turbo` need a quantized DiT file; the bf16 bundle itself only runs `reference`. `moss-infer quantize`
produces INT8 ConvRot files on Turing (5.04 GB for the 5B DiT in 49 s), and a community `convrot_w4a4` file runs as it
is. Measured on an RTX 2080 8 GiB, 256^2: 0.12 s/step (INT8, 5.3 GiB peak) and 0.14 s/step (INT4, 3.1 GiB) against
0.94 s/step for bf16. `docs/sm75-quantization.md` has the tier table, the INT4 writer gap and the plan for 8-bit
attention on Turing.

## Performance

Measured on an RTX 2080 Ti 11 GiB, MOSS-Image SFT, `balanced` mode, warm runs (models resident, prompt cached), the
bf16 text encoder from the bundle:

| Configuration | Size | Denoise step | Device peak |
|---|---|---|---|
| bf16 bundle, `reference` | 256² | 0.175 s | 10.1 GiB |
| INT8 ConvRot DiT, `high` | 256² | **0.091 s** | 6.3 GiB |
| INT4 ConvRot DiT, `turbo` | 256² | 0.103 s | 4.1 GiB |
| INT8 ConvRot DiT, `high` | 1024² | **2.58 s** | 7.5 GiB |
| INT4 ConvRot DiT, `turbo` | 1024² | 2.59 s | 5.3 GiB |

The VAE decodes in fp32 on sm_75: about 0.2 s at 256² and 7.8 s at 1024². An 8 GiB card (RTX 2080) also runs all three
tiers, with the bf16 text encoder streamed.

### Profiling on Turing

Nsight Systems profiles the whole pipeline (`nsys profile --trace=cuda,cublas,nvtx --stats=true moss-infer generate ...`);
Nsight Compute's counters need `ERR_NVGPUCTRPERM` permission that an unprivileged account does not have.

What the timeline shows on an RTX 2080 8 GiB, `reference` tier, 256^2, four steps: about 3.0 s of host-to-device copies
(36 GB of streamed weights at ~12 GB/s) against ~3.1 s of kernels, so streaming is half the work. The largest kernels
are cuBLASLt's fp16 GEMMs (~35 %), the VAE convolutions (the single biggest kernel in img2img, 52.6 % of its kernel
time before the vectorisation below) and the sm75 conversion kernels. At 1024^2 the decode's fp32 convolutions cost
10-12 s before the optimisations below.

The kernels this backend owns were optimised from that profile: `conv2d_f32_sm75` now uses float4 shared-memory loads
and float4 accumulators (four input channels per FMA) with vectorised float4 output stores (VAE decode 0.37 -> 0.20 s at
256^2 and 10-12 -> 7.8 s at 1024^2; encode 0.39 -> 0.19 s), `gemm_out_f32` loads float4 and stores packed bf16
(176 -> 93 ms per four-step run), and `bf16_to_f16_rows_scaled` uses packed pair loads/stores (both fall back to one
column per thread for rows that are not aligned for it). The exact attention kernel is next: it kept its 64-query tile but now loads the Q fragments straight from global memory instead of staging them in shared memory, which lets three blocks share an SM instead of one, and it uses eight warps for the text encoder's head_dim 256 (four for the DiT's 128): the 1024^2 DiT attention call went from 32.8 to 14.3 ms (3.2 to 7.3 TFLOPS) and the text encoder's from 29.4 to 17.3 ms (7.9 TFLOPS).

## Numerics

- bf16 → fp16 is exact for values in fp16's normal range, so the converted operands are the same numbers the sm_80
  kernels see. Accumulation stays fp32 where the sm_80 kernel accumulates in fp32, and every output is rounded once
  from fp32 (the GEMM's bias is added in fp32 first, as cuBLASLt's bias epilogue does on sm_80).
- Attention, GEMMs and the VAE therefore differ from an sm_80 run only in accumulation order and rounding, not in the
  values fed in. Attention's probabilities enter P·V as fp16 (bf16 on sm_80), and the VAE computes in fp32 (TF32 on
  sm_80). INT8 GEMM results are bit-identical (exact int32 accumulation).
- The reference vectors under `tests/data` are recorded on sm_89; as on sm_120, tests that compare against them run
  with noise-class gates off that architecture.
- A GEMM input row whose largest magnitude exceeds fp16's 65504 is multiplied by the power of two that brings it in
  range and the output row by its inverse, both exact; only the row's values that the scale pushes below ~6e-5 lose
  precision. Weights and attention operands are converted unscaled: above 65504 they would become inf, below ~6e-5
  they lose precision (fp16 subnormals); the model's weights and q/k/v are inside that range in practice.

## Verification

- `tools/sm75_check.cu` (not installed, built with `MOSSINFER_SM75=ON`; every case passes on an RTX 2080 Ti) runs the
  Turing kernels against host references: dtype conversion, exact attention at both head dimensions and engine-shaped varlen/GQA cases (also
  causal with key lengths unlike the query lengths, and that q/k/v are left untouched), the fp16 GEMM (bf16 and f32
  out, a row above fp16's range, several row chunks), the INT8 GEMM (bit-exact), and the VAE convolution and attention.
- `tests/unit/test_sm75.cpp` covers the build's presence and, on a Turing device, the weight conversion round trip and
  the GEMM rows' per-row scale. Both pass on an RTX 2080 Ti.
- The VAE encoder and the merged-LoRA path are exercised on the RTX 2080: `--init-image`, `--reference` and `--hires`
  produce images (the encoder runs the same fp32 SIMT convolutions as the decoder), and `--lora` reports its adapters as
  `merged` in the report and changes the image at the expected strength.
- End to end on an RTX 2080: `moss-infer generate` and `moss-server` (protocol 2) produce the same PNG bytes for the
  `reference`, `high` and `turbo` tiers; the report's `quality.gpu_arch` is `sm_75`. On an RTX 2080 Ti, separate
  `moss-server` processes produce the same PNG bytes at all three tiers, at 256² and (`high`, `turbo`) 1024².
- A build with `MOSSINFER_SM75=OFF` compiles and links unchanged and keeps the same CPU test baseline.

## Limits on sm_75

- 8-bit attention: `q8_fp16` runs when asked for (a Turing INT8-QK kernel; `tier high` accepts a bf16 DiT with it;
  Volta has none); `q8_fp8` is
  refused (no e4m3 MMA on Turing). On Turing the INT8 MMA does the same MACs per instruction as the fp16 one, so
  `q8_fp16` is a bandwidth/footprint path rather than a speedup (see `docs/sm75-quantization.md`).
- Native INT4 MMA and NVFP4: INT4 files run through the INT8 unpack fallback (correct and bit-exact; the planner
  prices it at about 1.5× a native INT4 step); NVFP4 files are refused on every non-Blackwell GPU.
- The fused DiT blocks and their CUDA graphs (the blocks run op by op).
- img2img, inpainting, reference images and the hires fix run: the VAE **encoder** uses the same fp32 SIMT
  convolutions as the decoder on Turing (a stride-2 downsample kernel included); its cost is under Performance above.
- Runtime LoRAs are **merged into the weights at load** instead of the sm_80+ fused side branches: the merge kernels
  are plain SIMT, run before the bf16-to-fp16 conversion, and the report says `merged` for their adapters. A strength
  change or a switch between stacks re-merges in place from the pristine bf16 copies and converts the rewritten
  resident weights to fp16 again; a stack that merges a module the loaded DiT never merged reloads it. Control adapters
  still need the fused LoRA path and are refused.
- Forced INT8 GEMM tiles (`Int8Tile`, a test and benchmark option): sm_75 runs one tile (64x128x64), so a forced tile
  is refused rather than ignored.

The VAE decode is fp32 SIMT on sm_75, so a 1024² decode costs about 11 s; a future fp16 path would cut that.
